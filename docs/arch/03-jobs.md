# 03 — Background work and durable state

> [!NOTE]
> Paths starting `src/` or `tests/` are relative to `core/`. Worker paths are given in full
> (`worker/encore_worker/...`). Line numbers (`:NN`) may have drifted; the named symbol is the authority.

**IDs:** `XR-JOB-nn`
---

## What this section covers

Everything that happens to a song when nobody is watching, and everything the box must still know
after it is turned off and on again. Concretely: the job ledger (`src/lib/server/jobs`) and the authoritative-state layer (`src/lib/server/state`, 3 files) — enqueue and
dedup, dispatch to a worker fleet the core does not control, leases and the reaper, retry and terminal
failure, and the write-behind snapshot of the queue and playback.

Five questions govern every row: **what happens to an in-flight job when the process restarts**,
**whether a step is idempotent under redelivery**, **how a failure becomes visible to a person rather
than only to a log**, **what bounds concurrency**, and **whether the state survives a crash at all**.

The subsystem is unusually well-reasoned in source — the pure/IO split (`transitions.ts` ↔
`repository.ts`, `leases.ts` ↔ `reaper.ts`) is real, and the comments carry the defect history. What
the rows below are for is the part that is _not_ in source: which of these behaviours are decisions
someone could reverse, and which are accidents nobody has been asked about.

A process is coordinated across two processes and two languages. The worker side of each
cross-process claim below is in `worker/encore_worker`: `transport/client.py` (the reconnect loop, the
heartbeat leg, and the worker's own accept/reject rule), `protocol/frames.py` (the handshake it adopts)
and `host/config.py` (the progress keepalive and the worker id). Every cross-process claim names the file
on both sides so a reader can check the pair rather than trust the prose.

---

## 0. Where the code contradicts the obvious reading — read this first

**The worker's two cadences adopt different things.** The core advertises `heartbeatIntervalSec` as
**half** the progress lease — `Math.floor(this.#config.progressLeaseMs / 1000 / 2)`
(`src/lib/server/jobs/worker-hub.ts`, with the margin argument in the comment above it) — and the
worker adopts it for the `worker:heartbeat` leg only (`Welcome.heartbeat_interval_sec` in
`worker/encore_worker/protocol/frames.py`, driving the heartbeat loop in
`worker/encore_worker/transport/client.py`). The **job progress lease** is refreshed by a separate
`KEEPALIVE_SEC = 10.0` (`worker/encore_worker/host/config.py`, overridable by `ENCORE_KEEPALIVE_SEC`)
that adopts nothing from the core. Two numbers in two languages must agree and only prose ties them.
See `XR-JOB-12`.

Two defects found by reading this subsystem are fixed, and their rows say how: a terminal failure's
gate settle was memory-only across a restart (`XR-JOB-04`), and the unservable-job TTL was evaluated
only when an unrelated event called `dispatch()` (`XR-JOB-11`).

### Negative findings — what was searched for and not found

- **No published standard governs any number in this section.** Lease durations, retry ceilings,
  keepalive cadence, an unservable TTL and a write-behind debounce are all engineering choices for a
  single-box self-hosted service with a fleet of one to a few workers. Every row whose subject is a
  duration or a count is therefore `UNSOURCED` **by necessity**, not by omission. None of the existing
  numbers is second-guessed here and no new number is invented.
- **No durable record of a process failure exists on the song.** There is no server-side
  `last_error` column; the reload signal is a per-device client scar (`src/lib/stores/process-scars.ts`).
  The failure _is_ durable in the attempt ledger (`job_attempts.error`) and readable at
  `GET /api/audit/[mediaId]`; what does not exist is a path from there to a guest's phone.
- **Nothing in the test tree drives a restart across a real SQLite file.** `recoverOnBoot` is covered
  (`tests/unit/server/jobs/reaper.test.ts`) and `flushNow` is covered
  (`tests/unit/server/state/state.test.ts`), but both run against an in-process repository. Every
  row whose subject is _what survives a restart_ therefore needs a test shape the repo does not yet
  have, and each says so rather than naming a file that would not exercise it.

## Group A — Restart, crash and recovery

### XR-JOB-01 — A core restart returns every in-flight job to the queue, and nothing resumes mid-step

| Field          | Content                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Statement**  | On core startup, every job in a non-terminal owned state (`assigned`, `running`) is returned to `queued` before the dispatch loop starts, and no code path attempts to resume a step from partial output. A restart costs the work in flight; it never costs the request.                                                                                                                                                                                                                                                                                                                                                    |
| **Surfaces**   | None directly (server subsystem). Phone renders the consequence as a process that restarts its progress bar; TV renders it as a song that stays held. Operator dashboards read the resulting attempt history.                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Rationale**  | Ownership of a job is a live WebSocket session, and after a restart there are no sessions by definition — so a job left `running` names an owner that cannot exist, and would sit unreaped until a lease that no longer has a live counterpart expires. Discarding partial work is the cheap half of the trade; the expensive half would be a resume protocol per step.                                                                                                                                                                                                                                                      |
| **Source**     | Cited. `src/lib/server/jobs/leases.ts` (`inflightToRecover` selects exactly `assigned`/`running`), applied by `src/lib/server/jobs/reaper.ts` (`recoverOnBoot`, firing the `RECOVER` event), called once at `src/lib/server/app.ts` — **before** `server.ts` starts the tick loop. `RECOVER` is a legal edge from both owned states and from nowhere else (`src/lib/server/jobs/transitions.ts`). No resume mechanism exists in the core: `job_attempts` records `startedAt`/`finishedAt` but no step cursor. (The worker keeps running a held job across a reconnect and re-claims it with `job:claim` — `_claim_pending` in `worker/encore_worker/transport/client.py`, answered by `#onClaim` in `worker-hub.ts`. A job boot recovery requeued no longer names that worker and is not `assigned`/`running`, so `#onClaim` answers it `revoked` and it is not that worker's to publish.) |
| **Acceptance** | **Given** a job persisted as `running` with a `workerId` and a lease, **when** the core starts, **then** before the first dispatch pass that job is `queued` with `workerId` null and `leaseExpiresAt` null. **Falsified by** a single job observed in `assigned` or `running` after `recoverOnBoot` returns, or by any code path that reads a partially-written artifact and skips a step.                                                                                                                                                                                                                                  |
| **Check**      | `tests/unit/server/jobs/reaper.test.ts` already pins the in-process half (two in-flight jobs recovered, a `queued` one untouched). What is **not** covered is the durable half — the same assertion across a real SQLite file closed and reopened. That test does not exist yet and would need writing; it is the only shape that distinguishes "the repository resets the row" from "the row was reset and written".                                                                                                                                                                                                        |
| **Priority**   | **Ship-blocking.** A single job stuck `running` after a restart holds its dedup slot forever, which makes the song un-processable rather than merely slow.                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

### XR-JOB-02 — A restart-recovered attempt is uncharged, and the redispatch it permits has a stated ceiling

| Field          | Content                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Statement**  | Boot recovery does not consume a job's retry budget — and because it does not, the product states what bounds a job that is recovered repeatedly, so a core that restarts during every process cannot redispatch the same job without limit.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **Surfaces**   | None directly. Phone renders it as a process that never finishes and never fails; operator dashboards render it as an unbounded run of `abandoned` attempts on one job.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **Rationale**  | "A core restart isn't the worker's fault" is correct as a fairness rule and incomplete as a policy: it removes the only counter that ends the loop. A crash-looping core and a worker that reliably kills the box are indistinguishable from inside the ledger, and the second is the case where uncapped retry does real harm — it spends the fleet forever on a job that will never complete.                                                                                                                                                                                                                                                                                                                                                          |
| **Source**     | `DERIVED` for the loop; cited for the mechanism. **Model:** `attempts` is preserved verbatim on recovery (`src/lib/server/jobs/leases.ts`, and `reaper.ts` reads the pre-recovery count back off the in-flight row through `#jobByIdAttempts`, `:96`), and `RECOVER` is a member of both `OUTCOME_FOR_EVENT` (`src/lib/server/jobs/repository.ts`, sealing the dying attempt `abandoned`) and `REQUEUE_EVENTS` (`:56`, opening a fresh one). So each restart appends exactly one sealed `abandoned` attempt and leaves `attempts` where it was, while `attemptsExhausted` (`leases.ts`) — the only thing that ends a job — reads `attempts` alone. The conclusion is by enumeration of the counters, not by observation: **no crash loop was executed.** |
| **Acceptance** | **Given** a job recovered N times with no worker ever completing it, **when** N grows, **then** the product's stated ceiling is reached and the job becomes terminal with a reason naming the restart loop. **Falsified by** a job whose `attempts` is still 0 after 50 recoveries with 50 `abandoned` rows in its ledger — which is the behaviour today.                                                                                                                                                                                                                                                                                                                                                                                                |
| **Check**      | `EXEMPT` from a source scan: the question is a policy that does not exist yet, so there is nothing to assert against. Once a ceiling is stated, the mechanism is testable in-process by looping `recoverOnBoot` against the existing `tests/unit/server/jobs/reaper.test.ts` harness and asserting the terminal transition — the judgment deferred is the ceiling itself, and what it should count (recoveries, wall-clock age, or ledger rows).                                                                                                                                                                                                                                                                                                         |
| **Priority**   | **Should ship.** The failure mode needs a crash-looping core, which is rare and loud; but the cost while it lasts is the whole fleet, and the ledger's own audit trail is what grows without bound.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |

> **Recommendation (not decided).** Do not charge a recovery against `attempts` — the fairness
> argument in `leases.ts` is right. Bound it on a **different axis instead**: fail a job whose
> ledger holds more than a stated number of `abandoned` attempts with zero `startedAt` stamps, which
> is precisely the signature of work that is dispatched and never begins. That reads off columns the
> ledger already writes (`attempts.ts`), needs no new state, and leaves an honest retry — a
> worker that genuinely tried and died — untouched.

### XR-JOB-03 — Authoritative room state loses at most one stated window to an ungraceful stop

| Field          | Content                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **Statement**  | The queue and playback are held in memory and snapshotted write-behind, and the product **states the window of mutations an ungraceful stop discards** — a power cut, an OOM kill, `docker kill` — as a duration, not as "small".                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Surfaces**   | Phone and TV both render the post-restart queue, so a lost mutation is a song that a guest watched themselves add and that is no longer there. Operator dashboards unaffected.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Rationale**  | Write-behind is the right choice on the hot path and the loss window is the price of it. Unstated, the price is paid by whoever is standing in the room when it happens and cannot tell a lost add from a bug — and "the queue is small (a party)" argues that a _flush_ is cheap, which is a different claim from the loss being acceptable.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Source**     | Cited for the mechanism, `UNSOURCED` for the acceptable window. `src/lib/server/state/store.ts` sets `flushDelayMs = 250`; `#scheduleFlush` coalesces a burst into one trailing write, so the exposure is bounded by the debounce rather than by the mutation rate. `flushNow()` is wired to **`SIGTERM` and `SIGINT` only** (`gracefulShutdown`, `server.ts`), which are exactly the signals an ungraceful stop does not send. Persistence is replace-the-world per room inside one transaction (`src/lib/server/state/persistence.ts`), so a torn snapshot is not a failure mode — a lost one is.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **Acceptance** | **Given** the stated window W, **when** the process is killed uncatchably at any point, **then** the rehydrated queue is missing at most the mutations of the last W. **Falsified by** a restart that drops a mutation older than W — for instance any state written by a path that mutates memory without calling `#scheduleFlush`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Check**      | `gracefulShutdown` in `server.ts` exits non-zero when the flush fails; that exit code is **unpinned** (importing `server.ts` into `bun test` would start the server, so only a source scan could check it), and a stop that lost pending queue state could read as healthy to Docker or systemd with nothing to notice. `tests/unit/server/state/state.test.ts` covers `flushNow`. Neither could observe the loss window, which needs a test the repo does not have: mutate, kill without a signal, reopen the same database file, compare. Written as a source-level guard instead, the tractable half is an enumeration that every mutating method on `AuthoritativeState` calls `#scheduleFlush` — today `applyQueueOp`, `reorder`, `setPlayback` and `setPosition` all do (`store.ts`), and a future fifth that does not would make the window unbounded for that state rather than merely 250 ms. |
| **Priority**   | **Should ship.** The number is already conservative; what is missing is that it is written down and that the enumeration keeping it true is enforced.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |

### XR-JOB-04 — A settled readiness gate is durable, or it is recomputed at boot

| Field          | Content                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Statement**  | When a process reaches a terminal state — failed, or cancelled — the readiness gate it settles is **either persisted with the settle or re-derived at boot from the job ledger**. A restart must not be able to restore a song to "processing" when no job is processing it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Surfaces**   | Phone (a stranded row shows a progress line and no Sing button, so the guest has no affordance to recover it); TV (rotation holds the entry and skips it every pass).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Rationale**  | The gate is what rotation consults, so a gate stuck mid-flight is not a cosmetic error — it removes the song from the party and removes the guest's way to ask for it again. The subsystem already recognises this as its worst failure class and fixed it three times for three fail paths; the restart is the fourth door into the same room.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Source**     | Cited; **both halves ship.** Why the rule is needed: the processing flip is persisted — `src/routes/api/process/+server.ts` upserts the media right after `requestProcess` sets `stemStatus = 'queued'` (`src/lib/server/jobs/process.ts`); `stem_status` and `lyrics_status` are stored columns (`src/lib/server/db/schema.ts`) read back verbatim (`src/lib/server/media/repository.ts`); and `hydrateMediaCatalog` fills the runtime map from those rows at boot (`src/lib/server/app.ts`), so a settle that lived only in memory would be undone by a restart. How it holds: (1) `TerminalFailureDeps.persist` (`process.ts`) is the sink, optional in the type and required for durability, and `WorkerHub.terminalFailureSinks()` (`worker-hub.ts`) is the one bag every terminal path passes, the reaper's `onFailed` included (`app.ts`); (2) `reconcileStrandedGates` (`src/lib/server/jobs/gate-reconcile.ts`) runs synchronously in `app.ts` immediately after `hydrateMediaCatalog`, with `findLiveJob` and `persist` deps, and re-derives every gate the stored row claims is in flight while the ledger holds no job that could settle it. Both settle through the shared `GATE_SETTLEMENT` table (`process.ts`), which `settleGatesForFailedJob` and the boot pass both read. |
| **Acceptance** | **Given** a process that reached terminal `failed` (or was cancelled) and settled its gate, **when** the core is restarted, **then** the song rehydrates un-processed and offers Sing. **Falsified by** one observation: a song whose newest job row for `fetch`/`stems` is `failed` or `canceled` while its media row still reads `stem_status = 'queued'` after a boot.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Check**      | `tests/unit/server/jobs/terminal-failure-durability.test.ts` (the in-process half) and `tests/unit/server/jobs/gate-reconcile-boot.test.ts` (the boot half's behaviour). The first drives the worker-reported paths and the reaper path through `hub.terminalFailureSinks()` and asserts the row is persisted. The second asserts the boot pass's safety: a `queued`/`assigned`/`running` job of **any** type that could settle a gate protects it (so a song mid-`fetch` is not clobbered for having no `stems` job yet), a healthy completed song and a never-processed song are untouched, and a second run settles and writes nothing. **The boot pass's wiring is unpinned:** those arms call `reconcileStrandedGates` directly, so `app.ts` could stop calling it, call it before `hydrateMediaCatalog`, or pass a `findLiveJob` that always answers "nothing is live" without a test reddening. |
| **Priority**   | **Ship-blocking, and shipped.** A violation is one a guest cannot work around, it is reached by an ordinary restart rather than by a rare race, and without the boot pass the recovery is a manual database edit.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |

> **Decided — both the sink and the boot pass.** They cover different windows. The sink makes a _live_
> failure durable at the moment it happens, so a song is never briefly observable as stranded between
> the failure and the next restart. The boot pass makes the invariant hold for every _other_ way a gate
> goes stale — a row stranded before the sink existed, a crash between the settle and the write, a job
> row deleted with its dedup slot — none of which any write can reach. The shared `GATE_SETTLEMENT`
> table declares the per-type rule once and both halves read it, so a future pipeline step cannot be
> added to one and forgotten in the other.

## Group B — Idempotency, dedup and retry

### XR-JOB-05 — At most one live job per (song, step), enforced by the database and not only by the application

| Field          | Content                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Statement**  | Two requests for the same step of the same song produce **one** job, and that uniqueness is enforced by a database constraint as well as by the application's lookup — so a concurrent second request cannot create a duplicate between the read and the write.                                                                                                                                                                                                                                                                                                      |
| **Surfaces**   | None directly. Phone renders the consequence: a second guest queueing the same song subscribes to the process already running rather than starting a second one.                                                                                                                                                                                                                                                                                                                                                                                                     |
| **Rationale**  | Dedup here is not an optimisation but the mechanism that makes the whole request path idempotent — every retry, every reconnect resend, every second tap relies on it. An application-only check is a read followed by a write, and the two requests that matter arrive over two transports at once.                                                                                                                                                                                                                                                                 |
| **Source**     | Cited. Both halves exist. Application: `findLive` (`src/lib/server/jobs/repository.ts`) excludes only `SLOT_FREEING_STATUSES = ['failed', 'canceled']` (`:26`), so a `ready` job still holds the slot; `enqueue` (`:120-122`) returns the existing live job untouched, without opening a new attempt. Database: the partial unique index `jobs_live_media_type_idx` on `(media_id, job_type) WHERE status NOT IN ('failed','canceled')` (`src/lib/server/db/schema.ts`) — the same predicate, which is what makes the two agree by construction rather than by hand. |
| **Acceptance** | **Given** an existing live job for `(m, stems)`, **when** a second request enqueues `(m, stems)`, **then** the same job id is returned, no second `job_attempts` row is opened, and the `singerId` attribution stays with the original requester. **Falsified by** two rows in `jobs` for one `(media_id, job_type)` neither of which is `failed` or `canceled`.                                                                                                                                                                                                     |
| **Check**      | `tests/unit/server/jobs/repository.test.ts` covers the application lookup. The **index** predicate and the constant are two statements of one rule in two languages, and the honest guard is a source-scan asserting `SLOT_FREEING_STATUSES` and the index's `WHERE` clause name the same statuses: read the other statement of the rule as text and compare the two token lists. `tests/unit/server/jobs/outstanding-job-parity.test.ts` keeps two repository queries (`findOutstandingForMedia`, `mediaWithOutstandingJob`) agreeing status by status; nothing compares either to the index. **The index parity assertion does not exist.**                                                                                                          |
| **Priority**   | **Ship-blocking**, and it is the cheapest row here: both mechanisms already ship correctly, and what is missing is the guard that stops them diverging.                                                                                                                                                                                                                                                                                                                                                                                                              |

### XR-JOB-06 — Re-running a finished step has one stated mechanism

| Field          | Content                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Statement**  | The product has **one** documented way to make a step that already succeeded run again, and every caller that needs a re-run uses it. Two mechanisms for one need is a defect, not a choice.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **Surfaces**   | Phone (the human lyrics re-pick is the only user-facing re-run today); operator dashboards (a future re-process control would be the second).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Rationale**  | A `ready` job occupies the dedup slot on purpose — that is what stops a re-queue burning GPU on an identical instrumental — so every re-run has to defeat the same guard, and each new caller that invents its own way to do it is a new way to leave the ledger inconsistent.                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **Source**     | Cited, and the two mechanisms are both in `main`. `supersedeForRerun` (`src/lib/server/jobs/repository.ts`) deletes the terminal slot occupant so a fresh `enqueue` runs, guarding that only a terminal occupant is removed and leaving the attempt history intact. The lyrics re-pick (`requestLyricsReselect`, `process.ts`, whose doc comment states that the slot must be freed before the enqueue) uses **cancel-then-enqueue** when an `align` is still live and calls `supersedeForRerun` only when the occupant is terminal. So one function documents itself as the durable seam for exactly this problem and the only live re-run uses it on one of its two branches. |
| **Acceptance** | **Given** the stated mechanism, **when** every call site that re-runs a finished step is enumerated, **then** each uses it; **and given** a re-run, **then** the prior attempt rows survive and exactly one new job exists for the key. **Falsified by** a second re-run path that reaches `queued` by different means, or by a re-run that leaves both an old and a new live row for the key.                                                                                                                                                                                                                                                                                                                                                              |
| **Check**      | A source-scan enumerating writes that clear a terminal occupant — `delete` against `jobs`, and `cancel()` on a job the caller is about to re-enqueue — and asserting each routes through the named mechanism. `tests/unit/server/jobs/lyrics-reselect.test.ts` covers the re-pick's behaviour but not its uniqueness as a mechanism; the enumeration does not exist yet.                                                                                                                                                                                                                                                                                                                                                                                    |
| **Priority**   | **Should ship.** One re-run path ships and works; the cost is paid by the second one, which the register expects (a re-process control) rather than observes.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |

### XR-JOB-07 — The retry ceiling is stated per step class, or stated to be uniform on purpose

| Field          | Content                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Statement**  | The number of processing attempts a job gets before terminal failure is stated as a policy — including "the same for every step" as a legitimate stated answer — and where a step's cost differs by orders of magnitude, the policy says why the same ceiling still applies.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Surfaces**   | None directly. Phone renders it as how long a song tries before giving up; the fleet pays for it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| **Rationale**  | Three attempts is generous for a two-second metadata fetch and expensive for a forty-minute separation on a shared box, and the same constant governs both. That may well be right, but it is currently an inherited default rather than a decision, and the retry ceiling is the one number that multiplies every other cost in this subsystem.                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| **Source**     | `UNSOURCED` for the number, cited for the mechanism and for the cost asymmetry. The ceiling is one rule in one place — `attemptsExhausted(attempts, maxAttempts)` (`src/lib/server/jobs/leases.ts`), whose comment records that it was previously inlined in two sites that had to stay in lockstep by hand, and which explicitly names "a per-job-type cap" as the change it was extracted to make possible. The value is set per job at `repository.ts` (`maxAttempts: 3`) with the column defaulting identically (`schema.ts`). The asymmetry is the subsystem's own claim: `dispatch.ts` argues a `stems-upgrade` must not inherit its parent process id precisely because "a 43-minute upgrade would be folded into a process that actually delivered a singable song in 90 seconds". |
| **Acceptance** | **Given** the policy, **when** a reader asks how many times a separation is retried and how many times a metadata fetch is, **then** they find an answer for each; **and given** a job of a class whose stated ceiling is N, **when** its Nth attempt fails, **then** it reaches terminal `failed` and no N+1th is dispatched. **Falsified by** a `stems` job observed on a fourth attempt, or by a policy document that states one number without saying it is deliberately uniform.                                                                                                                                                                                                                                                                                                      |
| **Check**      | `tests/unit/server/jobs/leases.test.ts` pins `attemptsExhausted`, and `tests/unit/server/jobs/reaper.test.ts` drives a job to terminal `failed` through the real exhaustion path. Both are ceiling-agnostic, which is correct — they check the rule, not the number. What a stated per-class policy would additionally need is an assertion that `enqueue` derives `maxAttempts` from the job type rather than from a literal, so a class without a stated ceiling is a failure rather than a silent 3.                                                                                                                                                                                                                                                                                    |

## (a) Requirements deliberately NOT written, and why

1. **The job state machine's legality rules.** `transitions.ts` is a pure, exhaustive, event-keyed
   table with terminal states having no outgoing edges, and `tests/unit/server/jobs/transitions.test.ts`
   pins it. The design note explaining why it is keyed on the _event_ rather than a status pair
   (`assigned → queued` is both a reject and an ack-timeout) is better than a requirement restating it.
2. **That the ledger is optional and can never break a process.** Stated and enforced in three places:
   the `AttemptLedger` is a nullable constructor argument (`repository.ts`), the slot-release
   hook is opt-in (`:102`), and `#patchOpen` is a documented no-op when no attempt is open
   (`attempts.ts`). This is a good rule that was never at risk.
3. **Slot-release event membership.** Which events free a worker's concurrency slot is one of the
   subtlest rules in the subsystem — `FAIL` and `CANCEL` are deliberately excluded because they are
   not exclusively worker-reported, and the explicit `registry.releaseSlot` calls live at the
   worker-report call sites in `worker-hub.ts`. The reasoning sits beside `SLOT_RELEASING_EVENTS` in
   `repository.ts`, and two tests pin it: `tests/unit/server/jobs/transitions-ledger-and-slots.test.ts`
   (which events fire the hook) and `tests/unit/server/jobs/reaper.test.ts` (the reaper's terminal
   `FAIL` frees no slot). Nothing to add.
4. **Process-stage monotonicity on the phone.** `media-status.ts` records six measured backward
   jumps, three distinct causes, and the floor-not-passthrough rule that fixed them, enforced by
   `tests/unit/server/jobs/media-status.test.ts` driving a full chain. Stated, measured and
   guarded — a requirement here would be a description.
5. **Cancellation coverage across job types.** `CANCELLABLE_JOB_TYPES` is an exhaustive
   `Record<JobType, true>` so a fifth job type is a typecheck failure at that table, with
   `PIPELINE_JOB_TYPES` derived from its keys so the loop bound cannot drift
   (`cancel.ts`). The exhaustiveness rests on the typecheck alone — the strongest shape in the
   subsystem; no test re-derives the `JobType` union independently.
6. **Process attribution and priority starvation.** `reprioritize-process.ts` is narrow, documented, only
   ever lowers a priority, and is safe to fire on every add; `repository.ts` explains why it
   cannot go through the state machine. The behaviour is covered by
   `tests/unit/server/jobs/reprioritize-process.test.ts`; its one call site, in `app.ts`, is unpinned.
7. **Specific values for the lease, the TTL, the debounce or the process cap.** No source supports any of
   them and inventing one would present a choice as a finding. Each appears above as a _stated-policy_
   requirement, never as a number this document chose.
8. **A durable server-side failure record on the song.** The mechanism is the client scar
   (`process-scars.ts`); `XR-JOB-09` requires its _scope_ to be stated rather than its mechanism
   reopened.
9. **Authentication on the audit and metrics surfaces.** Recorded as a finding rather than written as
   a row, because it belongs to an auth section and not to this one: `GET /api/audit/[mediaId]` states
   in its own header that it is "Ungated, same as /api/metrics", and both expose worker ids, model
   names and raw error strings (for audit, `audit/[mediaId]/audit-shape.ts`) — to an un-joined caller, which is a wider audience than
   `can()`'s "any joined singer" policy (`capabilities.ts`). `XR-API-11` carries it.
10. **Multi-room job scoping.** Jobs are keyed by media and never by room, which is correct — a processed
    instrumental is a deployment-wide asset. The room-scoped half of the state layer
    (`persistence.ts`) is already threaded and documented. Not a jobs question.

## (b) Open questions

Three rows above resolve to a number or a scope that is not yet stated. Each is laid out so it can be
settled without discussion.

**Q1 — What bounds a job that is recovered by boot forever?** (`XR-JOB-02`)
**A** — nothing; accept that a crash-looping core redispatches indefinitely. _Cost:_ zero code; spends
the fleet and grows the ledger without bound for as long as the loop lasts.
**B** — fail after N `abandoned` attempts that never reached `startedAt`. _Cost:_ one query over
columns the ledger already writes; needs a stated N. **Recommended in `XR-JOB-02`.**
**C** — fail on wall-clock age since the job's `createdAt`. _Cost:_ same shape, but also kills a job
that has been waiting legitimately for a worker to come up, which is the common self-hosted case.

**Q2 — Is the retry ceiling per job type?** (`XR-JOB-07`)
**A** — uniform 3; state that it is deliberate. _Cost:_ one line of documentation.
**B** — per type, with `stems-upgrade` at 1. _Cost:_ `enqueue` derives `maxAttempts` from the job type;
one constant per type. **Recommended in `XR-JOB-07`.**
**C** — per type and operator-configurable. _Cost:_ four new settings fields and a normalizer, for a
knob nobody has asked to turn.

**Q3 — Is a process failure per-device by design?** (`XR-JOB-09`)
**A** — yes; state it. _Cost:_ one line. A second guest's phone never learns, which at a co-located
party is arguably fine because the first guest is standing right there.
**B** — yes, plus a "why?" link into the existing audit endpoint. _Cost:_ one link; no new state, no
migration. **Recommended in `XR-JOB-09`.**
**C** — broadcast the failure to every phone. _Cost:_ a room-wide notice for one guest's failed
process; `RoomLink` (`src/lib/stores/room.ts`) deliberately keeps the failure notice personal.
