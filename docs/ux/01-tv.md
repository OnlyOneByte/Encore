# 01 — TV surface requirements

IDs `XR-TV-nn`. Surface under specification: `/tv` — a shared display read at 8–12 ft, with
**no pointing device and no keyboard in the room's hands**. Where a requirement also constrains
the phone or an operator page, that is stated in **Surfaces**; nothing here says "all".

**Provenance notes that apply to every row below.**

- WCAG success criteria are cited by number, name and a `w3.org/TR/WCAG22` anchor.
- **Broadcast safe-area figures (5 % action-safe / 10 % title-safe) are marked
  `UNSOURCED (broadcast convention)`.** The convention is real and near-universal (EBU R 95 for
  16:9 production; Google TV and tvOS both publish a 5 % overscan allowance), but **no URL was
  verified in this session**, so the figures are renegotiable on evidence rather than settled.
- **`DERIVED` rows state their model.** The angular model used throughout is: *angular size from
  panel diagonal + viewing distance + the CSS viewport the browser presents* (a UHD TV browser
  presents a **fixed 1920×1080 CSS viewport regardless of panel pixels** — Samsung's UHD groups
  report 1920×1080, FHD groups 1280×720), giving **~0.70 arcmin per CSS px on a full-panel
  1080-tall viewport**, near-identical at 43″@8 ft, 55″@10 ft and 65″@12 ft. CSS's nominal
  reference pixel is 1.28 arcmin, so a TV CSS px carries **~0.55×** the intended angle and every
  phone-derived coefficient is **~1.8× too small**.
- **What was looked for and not found:** no published standard sets a *minimum type size* for a
  web document on a television. Google's and Apple's TV guidance both start at **24 px**, which
  the 1.8× correction reproduces independently (16 × 1.8 ≈ 29 px), but neither is normative and
  neither is a conformance criterion. There is also **no API by which a browser can observe
  anything physical**: absolute units are pinned at 1 in = 96 px, `devicePixelRatio` is
  CSS-px-to-device-px and not physical DPI, `ScreenDetailed` carries no physical dimensions, and
  Tizen/webOS expose panel size only to *packaged* apps. **Viewing distance is unobservable by
  any API.** Every number below is therefore a design constant, not a measurement the product
  can make at runtime.

## Group 1 — Per-surface property floors

### XR-TV-01 — The TV type floor lives in exactly one declaration

| Field | Content |
|---|---|
| **Statement** | The root font size is `calc(max(2.7vh, 20px) * var(--ui-scale))`, and **every** TV type tier is a `rem` multiple of it. No TV tier is smaller than `0.93rem`. |
| **Surfaces** | TV (the root declaration is global, so it also raises the phone's root — see XR-TV-02's note) |
| **Rationale** | A browser cannot detect whether the document fills the panel, so both cases must be satisfied at once by a `max()` of a panel-proportional term and a windowed-browser term. |
| **Source** | `DERIVED` — the angular model in the provenance note above: `2.7vh` = 29.16 px at a 1080-tall viewport = 16 px × 1.8. The `20px` term is the windowed case (`2.2vh` on a 900 px-tall laptop viewport = 20 px), below which every physical assumption collapses. Ratified in `encore-design-handoff.md` §1 "TV type floor — DECIDED". |
| **Acceptance** | *Given* `/tv` at a 1920×1080 CSS viewport and `--ui-scale: 1`, *when* computed styles are read, *then* the document root computes to **29.16 px ± 0.5**, the smallest rendered TV tier computes to **≥ 27 px**, and **no** TV type declaration in `apps/core/src/lib/tv/**` or `apps/core/src/routes/tv/**` contains a `px` font-size literal. |
| **Check** | Source scan for `font-size` literals under the TV tree (extends `stage-scale.test.ts:37`, which today only rejects literals *below* the floor and would pass a hard-coded `44px`) + an in-browser computed-style probe at 1920×1080 for the root and tier values. The computed half **cannot** be a source scan. |
| **Priority** | **Must.** Current `--tv-eyebrow` (16 px floor) and `--tv-label` (20 px floor) fail at every resolution. |

Recorded ladder, expressed against a 29.16 px root so a reader can recompute it:
`--tv-small` 27 px = 0.926 rem · `--tv-body` 33 px = 1.132 rem · `--tv-name` 44 px = 1.509 rem ·
phrase 84 px = 2.881 rem · `--tv-lyric` 91 px = 3.121 rem · room code 88–96 px = 3.02–3.29 rem ·
takeover hero 104 px = 3.567 rem · next-up singer 132 px = 4.527 rem.

### XR-TV-02 — A viewport term is applied exactly once

| Field | Content |
|---|---|
| **Statement** | Once the root font size carries the `vh` term, **no** TV type token carries a viewport term of its own. Tokens express ratios; the root expresses scale. |
| **Surfaces** | TV |
| **Rationale** | Two `vh` terms multiply, so a token that keeps its own `clamp(…vh…)` under a `vh`-scaled root scales the panel twice and the ladder stops being a ladder. |
| **Source** | `DERIVED` — arithmetic: 13 of the current `:root` declarations contain `vh`, and 6 of them are TV type tokens declared as `clamp(px, Nvh, px)`. |
| **Acceptance** | *Given* `apps/core/src/app.css`, *when* the TV type tokens are read, *then* **zero** of `--tv-small`/`--tv-body`/`--tv-name`/`--tv-lyric`/`--tv-hero`/`--tv-joinurl`/`--tv-eyebrow`/`--tv-label` contains `vh`, `vw` or `vmin`, **and** the root font-size declaration contains exactly one. Geometry tokens (`--tv-safe-*`, `--tv-qr`) are the named exemption: they size boxes, not type, and are not multiplied by the root. |
| **Check** | Source scan of the `:root` block — countable, no rendering needed. |
| **Priority** | **Must.** This is the failure mode that turns the type-floor change from a fix into a regression. |

> **Consequence to decide, not defaulted:** the root declaration is global, so a `2.7vh` root
> also applies to the phone, where `vh` tracks a phone viewport and produces ~19 px on a 700 px
> tall browser view. Either the phone root is pinned separately or the TV root is scoped to the
> `/tv` document. **Whichever is chosen must be stated**, because "the floor lives in one
> declaration" and "the phone is unaffected" cannot both be true without one of the two.

### XR-TV-03 — Safe areas are hardcoded percentages, and title-safe exists as a token

| Field | Content |
|---|---|
| **Statement** | Every TV edge offset resolves from a safe-area token. Action-safe is `max(env(safe-area-inset-*), 5%)` of the corresponding axis; **title-safe is 10 %** and exists as its own token pair. All full-screen TV *content* (headline, roster, phrase panel, takeover text) positions from title-safe; only chrome pinned to the frame uses action-safe. |
| **Surfaces** | TV |
| **Rationale** | `env(safe-area-inset-*)` is specified for **non-rectangular** displays, so a rectangular TV correctly reports `0` and cannot express overscan — a hardcoded percentage is the only mechanism available. |
| **Source** | `env()` semantics: [MDN `env()`](https://developer.mozilla.org/en-US/docs/Web/CSS/env). Percentages: `UNSOURCED (broadcast convention)` — 5 % action-safe / 10 % title-safe, unverified this session. The `max(env(), pct)` form is `DERIVED`: it costs nothing today and improves automatically if the page is ever wrapped in a webview that *does* report insets. |
| **Acceptance** | *Given* `app.css`, *when* the token block is read, *then* a title-safe token pair exists and resolves to **192 px / 108 px at 1920×1080**; *and given* any TV state at 1920×1080, *when* each rendered element's bounding rect is measured, *then* no content element's rect falls outside the title-safe box and no chrome element's rect falls outside the action-safe box. |
| **Check** | Token existence by source scan; rect containment by the in-browser geometry probe (XR-TV-19). `stage-scale.test.ts:66` already bans *fixed px* edge offsets — that guard stays and is not restated here; what is unenforced is **which** safe box each class of element belongs to. |
| **Priority** | **Must** for the token's existence (there is no title-safe token today and the chosen design positions almost everything at it). |

> **Discrepancy to resolve before implementation.** The mockup declares `--safe-y: 54px` (5 vh),
> but the repo's `--tv-safe-y` is `max(40px, 6vh)` = 64.8 px, and its comment records that
> **54 px was rejected** for "sitting right on the ~5 % overscan boundary with zero margin". The
> repo's 6 vh is the ratified value; the mockup's 54 px is the earlier rejected one. Implement
> 6 vh and leave the mockup as the visual reference it is.

### XR-TV-04 — Dimmed TV text is measured on its composited colour

| Field | Content |
|---|---|
| **Statement** | Any TV text rendered at less than full opacity meets its contrast floor **as composited over the backdrop it actually paints on**, not as its token value. The takeover-dimmed join block specifically clears 3:1 at ≥ 24 px. |
| **Surfaces** | TV |
| **Rationale** | Opacity is applied after the token is chosen, so a value that passes as a token can fail as a pixel, and nothing in the tree measures the composited result. |
| **Source** | [SC 1.4.3 Contrast (Minimum)](https://www.w3.org/TR/WCAG22/#contrast-minimum) — large-scale text (≥ 24 px, or ≥ 18.66 px bold) takes the 3:1 floor, other text 4.5:1. Composited values `DERIVED` by alpha-compositing the token over `--bg` `#0b0b12` and applying the WCAG relative-luminance formula: `--ink-dim` `#9a9ab5` at 72 % → **4.18:1**; `--accent-ink` `#c4a9ff` at 72 % → **5.47:1**; `--danger` at 72 % → **4.09:1**; `--ink` at 72 % → **9.31:1**. |
| **Acceptance** | *Given* the decided 72 % dim on the join block, *when* each of its text runs is composited over its backdrop and measured, *then* every run ≥ 24 px clears **3:1** and every run below 24 px clears **4.5:1**. The 4.18:1 `--ink-dim` run therefore passes **only because `--tv-small` is 27 px** — dropping that tier below 24 px breaks it. |
| **Check** | A unit test that composites the declared opacity against the declared backdrop and asserts the ratio, reading both from tokens. **Must not duplicate the hexes** — `tests/guards/design-system/colors.test.ts` already hard-codes `#0b0b12` and `#1a1a28` as literal copies of `--bg` and `--card`, which is the silent-green class this check would otherwise join. |
| **Priority** | **Must** — the composited value is invisible to every existing contrast test. |

> Text over **arbitrary video** is a different problem and is **already** both stated and enforced
> (`lower-third-stroke.test.ts`, `lyrics-stroke.test.ts` pin the stroke that lifts text off an
> unknown frame). Not restated here.

### XR-TV-05 — Every TV animation stops, rather than shortens, under reduced motion

| Field | Content |
|---|---|
| **Statement** | Each animated TV surface — phrase crossfade, phrase advance, takeover entry, progress fill, visualizer — has a `prefers-reduced-motion: reduce` branch that **halts** the animation and holds a static frame. No TV animation merely shortens its duration under `reduce`. |
| **Surfaces** | TV |
| **Rationale** | The TV has no input device, so a room-facing "pause" control is impossible to operate; the media query is the only mechanism by which motion can be stopped at all. |
| **Source** | [SC 2.2.2 Pause, Stop, Hide](https://www.w3.org/TR/WCAG22/#pause-stop-hide) governs auto-updating content lasting over 5 s and requires a mechanism to pause it — the 8 s phrase cycle is exactly that shape, and **the TV can offer no such mechanism**, which is the honest reason `reduce` must fully stop rather than soften. [SC 2.3.3 Animation from Interactions](https://www.w3.org/TR/WCAG22/#animation-from-interactions) and [`prefers-reduced-motion`](https://developer.mozilla.org/en-US/docs/Web/CSS/@media/prefers-reduced-motion) for the mechanism. |
| **Acceptance** | *Given* the enumerated animated TV surfaces, *when* `prefers-reduced-motion: reduce` is emulated, *then* each one's `animation-play-state`/`animation-name` resolves to a halted or `none` state and two frames captured 10 s apart are byte-identical. |
| **Check** | Source scan for a `reduce` block per animated selector (extends `visualizer-motion.test.ts`, which covers the visualizer only) + a two-frame capture under emulated `reduce`. `motion.test.ts`'s existing outright ban on Svelte `transition:`/`in:`/`out:`/`animate:` directives already covers the *mechanism* and is not restated. |
| **Priority** | **Must** for the phrase cycle (a 24/7 wall display is the worst case for unstoppable motion); **Should** for the rest. |

### XR-TV-06 — No target size on the TV is derived from viewing distance

| Field | Content |
|---|---|
| **Statement** | Target-size floors on the TV are the **unscaled** CSS values. The room has no pointing device, so the target-size criteria apply **only** to the enumerated pointer-operable controls on the TV document: the fullscreen button and the autoplay-recovery affordance. No target dimension anywhere on the TV is multiplied by a distance factor. |
| **Surfaces** | TV (contrast with the phone, where every control is pointer-operated) |
| **Rationale** | Target size is a criterion about **pointing precision** — the size of a finger or cursor relative to the target — and pointing precision does not change with how far away the viewer sits; only **visual-angle** criteria scale with distance. |
| **Source** | [SC 2.5.8 Target Size (Minimum)](https://www.w3.org/TR/WCAG22/#target-size-minimum) (24 CSS px, AA) and [SC 2.5.5 Target Size (Enhanced)](https://www.w3.org/TR/WCAG22/#target-size-enhanced) (44 CSS px, AAA). Both are expressed in CSS px and neither references viewing distance. Contrast with [SC 1.4.4 Resize Text](https://www.w3.org/TR/WCAG22/#resize-text) and 1.4.3, which are about perception and therefore *do* scale — which is why XR-TV-01 exists and this row is its opposite. |
| **Acceptance** | *Given* the TV document, *when* every pointer-operable control is enumerated, *then* the list is exactly {fullscreen button, autoplay-recovery affordance}, each measures **≥ 44 × 44 CSS px**, and **no** target-size declaration on the TV contains a `vh`/`vw`/`vmin` term as its *minimum*. A `clamp(44px, …vmin, …)` that scales a target **up** is conformant; a floor expressed *as* a viewport term is not. |
| **Check** | Source scan enumerating `on:click`/`<button>` in the TV tree and asserting each has a 44 px floor. The two current controls already satisfy this (`.fs-btn` is `clamp(44px, 5.2vmin, 88px)`; the autoplay affordance is `inset: 0`, i.e. the whole viewport) — **this row exists to stop a distance-scaled floor being introduced**, not to fix a present defect. |
| **Priority** | **Must.** It is cheap and it forecloses the most likely misreading of XR-TV-01. |

## Group 2 — Token dimensions that must exist

The leverage here is **structural**: a floor a component has to remember is a floor that will be
forgotten. When these rows were written, six token dimensions had **zero** declarations — spacing/gap,
line-height, font-family, z-index, motion duration/easing, breakpoints — and ~391 literals lived in
them, because a "no literal that duplicates a token" guard can only compare against a token that
**already exists**.

**Five of the six now have scales** (`acfe674`, breakpoints separately via `384682f`):
`--space-*` ×10, `--lh-*` ×5, `--z-*` ×14, `--duration-*` ×4, `--bp-*` ×5. **Two gaps remain, both
deliberate or unrecorded rather than done:** `font-family` was never tokenised (still a raw literal at
`app.css:782`), and motion shipped **duration only** — there are no easing tokens. The rows below stand
as the requirement; treat them as satisfied for the five and outstanding for those two.

### XR-TV-07 — `--ui-scale` exists, is bounded, and its persistence scope is stated

| Field | Content |
|---|---|
| **Statement** | `--ui-scale` exists as a token with a declared default of `1` and clamped bounds of `0.8–1.6`, and the product has a **stated** policy — documented at its definition site — for **whose** preference it is on a shared screen, applied consistently. |
| **Surfaces** | TV; the setting surface that writes it (phone or operator page) |
| **Rationale** | The TV is shared by a whole party, so "a persisted user preference" has no single owner on that surface and the question must be closed rather than left to the first implementation. |
| **Source** | Bounds ratified in `encore-design-handoff.md` §1. Scope: `UNSOURCED` — a named-decision requirement. Precedent exists in the tree: `tvProgressStyle` and `lyricsScalePct` are both **room**-scoped, which is the shape a shared screen already uses. |
| **Acceptance** | *Given* the token definition, *when* it is read, *then* a default and both bounds are present; *and given* an out-of-range write (`0.5`, `9`, `NaN`), *when* it is read back, *then* it clamps to `0.8`/`1.6`/the default. The scope criterion is **the existence and consistency of the stated policy, not its content**. |
| **Check** | Unit test on the clamp (the `clampInt`/`normalizeRoomSettings` pattern already used for `lyricsScalePct` binds bounds to constants, so a bound change flows through) + a source scan for the documented scope note. |
| **Priority** | **Must** for existence and clamping; **Must** for the policy being written down. |

**Recommendation (not decided):** room-scoped, alongside `tvProgressStyle`, because the TV renders
one room's screen and a per-guest scale on a shared display would mean the last writer wins
silently.

| **Acceptance** | *Given* `--ui-scale: 1.6` and `lyricsScalePct: 300`, *when* the reel is rendered at 1920×1080 with the longest lyric line in the fixtures, *then* the reel's rect stays within `100vh − var(--tv-chrome-h)` and the sung line is not covered by the lower-third. Same assertion at `0.8`/`100`. |
| **Check** | In-browser measurement at the four corner combinations. **Not a source scan** — this is a measurement claim, and no source scan can make one. |

## Group 3 — States and flows

### XR-TV-12 — Every TV state is enumerated, and the inventory is closed

| Field | Content |
|---|---|
| **Statement** | A single enumeration names **every** screen the TV can present, and each one has a designed frame, a stated trigger, and a stated exit. The enumeration is: **attract · lobby · playing · next-up · still-cooking · skipping · autoplay-blocked · playback-failed (silent room) · join-origin-unreachable · loading**. Any state not in this list is a defect, and additions extend the list rather than bypassing it. |
| **Surfaces** | TV |
| **Rationale** | The state nobody enumerated is the state that ships undesigned — `/tv` previously collapsed "nobody here" and "four people here with nothing queued" into one identical screen. |
| **Source** | `DERIVED` from the implementation's own conditionals: `tvScreen()` in `apps/core/src/lib/tv/screen.ts` yields `attract`/`lobby`/`waiting`/`playing`; the route adds transients `next`/`error`/`waiting`/`loading`, plus `autoplayBlocked`, `playbackFailedReason` and `joinUnreachable`. The three takeover frames are ratified in `_NEW-TV-DECISIONS.md`. |
| **Acceptance** | *Given* the enumeration, *when* each entry is driven on a real instance at 1920×1080, *then* every entry renders a frame with no empty region where a designed element belongs; *and given* the TV route source, *when* its top-level rendering conditions are collected, *then* every condition maps to exactly one enumerated state and no condition maps to none. |
| **Check** | Source scan reconciling the route's conditions against the enumeration (catches a state added without a frame) + the geometry probe of XR-TV-19 over all ten. **Named exemptions:** `loading` and `join-origin-unreachable` are exempt from the *phrase system* only (XR-TV-16/17); neither is exempt from having a frame. |
| **Priority** | **Must.** This is the row that catches the instance nobody thought of. |

> **Non-exclusivity is part of the state model, not a detail.** `autoplay-blocked`,
> `playback-failed` and `join-origin-unreachable` can each coexist with `playing` and with a
> transient, and the route's own comment records a past defect where independent `inset: 0` panels
> at the same z-index stacked. The enumeration must therefore state, per pair, which wins — that
> statement is what XR-TV-10's tier assertion checks against.

### XR-TV-14 — The lobby shows the whole roster, and the step-down is a rule

### XR-TV-16 — The phrase set is admissible by construction

| Field | Content |
|---|---|
| **Statement** | Every phrase in the rotating set is **≤ 24 characters**, and the rule is enforced against the phrase **data**, not against the renderer. |

| **Rationale** | A phrase that overflows its box is a data problem with a rendering symptom, and checking the data is both cheaper and total. |
| **Source** | `DERIVED` from in-browser measurement at 84 px / weight 900 in the real 820 px panel: all seven admitted phrases fit within 2 lines (87 px or 173 px); a 30-character control ("Nobody is judging you tonight.") **overflows to 3 lines** (260 px); the widest single word, "Everyone", occupies 440 px of 820 px. **The measured evidence brackets [23 fits, 30 fails]** — the longest admitted phrase is "You know all the words." at 23 characters — so **24 is a chosen boundary inside that bracket with one character of headroom, not a measured threshold**. ## Group 5 — Verification

### XR-TV-19 — TV frames are verified numerically at exactly 1920×1080

| Field | Content |
|---|---|
| **Statement** | Every enumerated TV state is verified by measuring each rendered element's rect against its frame bounds and comparing `scrollWidth` to `clientWidth` for every text element, at a CSS viewport of exactly **1920×1080**. Captured frames stay under 2000 px on both axes. |
| **Surfaces** | TV |
| **Rationale** | The stage type scale is viewport-relative, so a frame captured at any other height measures a different design — and eyeballing a capture cannot see a 2 px clip or an element 6 px outside title-safe. |
| **Source** | `DERIVED` — the mechanism was already run over all six frames of `tv-chosen.html` (zero overflow, zero clipped text) and is reused rather than reinvented. The 2000 px cap is a tooling constraint: a larger capture is silently unreadable to the agent tooling that reviews it, costing the review rather than erroring usefully. |
| **Acceptance** | *Given* each enumerated state at 1920×1080, *when* the probe runs, *then* `documentElement.scrollWidth − innerWidth = 0`, every element's rect lies inside its declared safe box, and no text element reports `scrollWidth > clientWidth + 1`. |
| **Check** | An in-browser probe driven against a real instance. **Not a source scan.** The rendered-DOM unit rung is **blocked** — `bunfig.toml` preloads `tests/setup/svelte-dom-preload.ts` but does not alias the `$app`/`$env` virtual modules, so only components with zero `$app` imports can mount (documented at `tests/guards/subsystem-tv/wake-lock.test.ts:18-27`), which the TV route is not. |
| **Priority** | **Must.** A green suite is the floor, not the bar: the repo's own record is that every recent real defect was invisible to passing tests and surfaced only by driving the app. |

### XR-TV-20 — A source-scan guard that stops biting is a finding, not a number to lower

| Field | Content |
|---|---|
| **Statement** | Each TV design guard states the value it pins and carries a non-vacuity floor, and a floor that fires is escalated as a finding rather than adjusted. No TV guard duplicates a value it could read from the token layer. |
| **Surfaces** | TV; the guard suite generally |
| **Rationale** | A rule that stops biting looks identical to a rule that is working, so without a floor the migration's real hazard — guards silently ceasing to enforce — produces no signal at all. |
| **Source** | `DERIVED` from the quantified guard-retirement analysis: 242 cases across 38 design-enforcing files sort to 128 survive / 68 retarget / 27 retire / **19 at risk**, collapsing to 9 concerns of which **4 are measurement claims that no source scan can make**. The duplication clause has a concrete precedent: `tests/guards/design-system/colors.test.ts` hard-codes `#0b0b12`/`#1a1a28` as copies of `--bg`/`--card`, tied to them only by a trailing comment. |
| **Acceptance** | *Given* each TV guard, *when* the production declaration it pins is reverted in a throwaway tree, *then* that guard fails on a named assertion; *and given* each guard, *when* it is read, *then* it contains no literal copy of a token value it could import. |
| **Check** | Per-hunk mutation — revert one production hunk at a time and require a named red. A guard that survives its own mutation is enforcing nothing. |
| **Priority** | **Must** for anything guarding a decision in this section; the shape-versus-value distinction matters: a guard asserting a `clamp()` *shape* passes a useless `clamp(10px, 1vmin, 20px)`, so pin the value where the value is the point. |

## Requirements deliberately NOT written, and why

1. **Text stroke over arbitrary video.** Already both stated and enforced
   (`lower-third-stroke.test.ts`, `lyrics-stroke.test.ts`). Referenced in XR-TV-04 rather than
   rewritten as new.
2. **A ban on Svelte `transition:`/`in:`/`out:`/`animate:` directives.** `motion.test.ts` already
   rejects them outright. XR-TV-05 specifies only the unenforced half — that `reduce` must *stop*
   rather than shorten.
3. **The `--tv-chrome-h` reservation and its ResizeObserver override.** Four existing assertions
   cover it, and the reel-cap double-charge is closed. XR-TV-08 covers only the new
   risk: a second multiplier entering the expression.
4. **Fixed-px edge offsets on the stage.** `stage-scale.test.ts:66` already bans them. XR-TV-03
   specifies the unenforced part — *which* safe box each class of element belongs to.
5. **A hero-QR sizing rule.** `--tv-qr` exists as `clamp(300px, 26vmin, 460px)` and two
   assertions pin both the token and its use. The upward-failure defect it fixed is closed.
6. **A distance-scaled target size.** Deliberately excluded, and XR-TV-06 exists to forbid it:
   target-size criteria govern pointing precision, not visual angle.
7. **A pause/stop control for the phrase rotation.** SC 2.2.2 asks for one and the TV **cannot
   provide it** — there is no input device in the room. Rather than invent a control nobody can
   reach, XR-TV-05 routes the obligation to the `reduce` branch and records the gap honestly.
8. **Whether Skipping should escalate differently from the other two takeovers.** Flagged as an
   open sub-question in the decision record and **not defaulted** there. A requirement would be
   inventing the ruling.
9. **Whether the root type floor is scoped to `/tv` or applied globally.** Both halves of the
   ratified claim ("one declaration" and "the phone is unaffected") cannot hold at once; the
   choice is noted under XR-TV-02 as a consequence to decide, not written as a requirement.
10. **A minimum type size sourced to a standard.** None exists for a web document on a
    television. Google's and Apple's 24 px starting points are guidance, not conformance
    criteria; every figure in Group 1 is therefore `DERIVED` from the stated angular model or
    marked convention, and is renegotiable on better evidence.
11. **Absolute panel size, resolution or viewing-distance adaptation.** Unobservable by any
    browser API. Specifying adaptation to something the product cannot measure would be an
    unfalsifiable requirement.
