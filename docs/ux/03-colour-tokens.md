# 03 — Colour, palette and token-layer requirements

Area prefix `XR-COL`. Substrate: the ratified **Chromatic, 48-stop** player palette where the
player's colour *is* the UI accent (handoff §2), and its token-layer consequences (handoff §3).
All decisions below are the owner's; these rows only make them checkable.

WCAG criteria cited throughout:

- [1.4.3 Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) — 4.5:1 for body text.
- [1.4.11 Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) — 3:1 for UI objects and graphics.
- [1.4.1 Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) — colour is never the only carrier of information.

## Finding that precedes the contrast rows — the measured figures were taken against different surfaces

> **Corrected in #820.** The generator and the registry now live in the repo —
> `packages/shared/scripts/_player_palette.py` and `packages/shared/src/player-palette-48.json` —
> and the generator READS `--bg`, `--card` and `--card2` out of `app.css` instead of carrying its own
> copy, so the figures below are the pre-fix state. The regenerated registry clears every floor with
> margin > 0 (worst ink 4.56 against the real `--card`), and the lift now targets `4.5 + 0.05` so the
> next surface drift fails loudly rather than crossing a zero margin. Guards:
> `packages/shared/src/palette-registry-820.test.ts`.

`packages/shared/src/player-palette-48.json` exists. Top-level keys: **`surfaces`** and
**`variants`**. `variants` holds `uniform` and `chromatic`; each is `{ stops: [48], stats: {…} }`.
Each stop carries 18 fields: `i, name, hue, srgb_hue, L, chroma, fill, on_fill, ink_kind,
accent_ink, accent2, r_dot_bg, r_dot_card, r_label, r_ink_card, d_danger, d_warn, d_ok` — so the
four per-stop ratios and the three status-hue distances are already in the data, per stop.

**`surfaces` is `{bg: "#060a18", card: "#131a2e", card2: "#1a2238"}`.** The app's live tokens are
`--bg: #0b0b12`, `--card: #1a1a28`, `--card2: #212133` (`apps/core/src/app.css:7–10`). The
generator measured against a mockup substrate that is marginally darker than what Encore paints.

Re-measuring the four roles against the app's real tokens (`DERIVED` — model: WCAG 2.x relative
luminance over sRGB, the same `srgbToLinear` + `0.2126/0.7152/0.0722` implementation as
`packages/shared/src/colors.ts` `contrastRatio`, applied to `variants.chromatic.stops`):

| Role | Handoff figure (mockup surfaces) | Against app tokens | Verdict |
|---|---|---|---|
| dot on `--bg` (3.0 floor) | 3.76 | **3.73** (Orchid) | still passes |
| dot on `--card` (3.0 floor) | 3.29 | **3.27** (Orchid) | still passes |
| label on fill (4.5 floor) | 4.53 | **4.53** (Scarlet) | unchanged — surface-independent |
| **ink on `--card` (4.5 floor)** | 4.50 | **4.47** (Cobalt) | **6 stops fail AA** |

The six: **Cobalt 4.47, Denim 4.48, Magenta 4.48, Orchid 4.48, Rose 4.48, Fuchsia 4.49.**

This is not a challenge to the palette direction — it is the *same defect class the handoff names
as "do this first"*: a contrast measurement bound to a duplicated surface value rather than to the
token the app paints. The margin was ~0.00 to begin with (`min_ink_card: 4.5`), so any surface
drift at all was going to cross it. It is carried as `XR-COL-04`.

## Group 1 — The palette is a registry with one machine-readable source of truth

### XR-COL-01 — One generated registry, and it is the only place a stop's values exist

| | |
|---|---|
| **Statement** | The 48 stops exist in exactly **one** machine-readable artifact, generated by `packages/shared/scripts/_player_palette.py`, and every consumer (validator, picker, roster, docs, tests) reads its values from that artifact. |
| **Surfaces** | Phone, TV, operator dashboards, build |
| **Rationale** | 48 stops × 4 values = 192 hexes; any second copy is a copy that will drift, and a drifted `onFill` is an AA failure nobody can see in a diff. |
| **Source** | `DERIVED` — model: the repo's own documented failure mode. `packages/shared/src/colors.ts:255` keeps `DEFAULT_STAGE_COLOR` as a literal *only* because SQL cannot run an OKLCH conversion, and pays for it with a named drift guard in `colors.test.ts`. No consumer here has that excuse. |
| **Acceptance** | **Given** the registry artifact and the repo, **When** every `#rrggbb` literal in `packages/shared/src`, `apps/core/src` and any palette doc is collected, **Then** none of them equals a `fill`, `onFill`, `ink` or `accent2` value of any stop, except inside the registry artifact itself — **excluding pure `#ffffff` and `#000000`**, which are carved out because **12 of the 48 stops carry `on_fill: #ffffff`**, so without the carve-out this criterion criminalises all 52 `#ffffff` occurrences across 12 files in `src` and can never go green. The carve-out is safe precisely because white and black are not distinguishing: no stop's *identity* is white, so a stray `#ffffff` cannot silently become a drifted copy of one stop in particular. |
| **Check** | Source scan in the shape of the existing `design-system.test.ts` / `contrast.test.ts` scans: load the registry, glob the source tree, assert zero literal matches outside the artifact. |
| **Priority** | **Blocking.** A second source of truth cannot be retrofitted out once 192 hexes are loose. |

### XR-COL-02 — The registry regenerates byte-identically

| | |
|---|---|
| **Statement** | Running `packages/shared/scripts/_player_palette.py` against the committed inputs reproduces the committed registry byte-for-byte. |
| **Surfaces** | Build |
| **Rationale** | "Generated, never hand-edited" is only true if a hand edit is detectable. |
| **Source** | `DERIVED` — model: the freshness-guard pattern already used for generated CSS elsewhere in this codebase family (generator output compared to the committed file byte-for-byte). |
| **Acceptance** | **Given** a clean checkout, **When** the generator runs to a temp path, **Then** the output is byte-identical to the committed registry; **and when** any hex in the committed registry is edited by hand, **Then** the same comparison fails naming the edited stop. |
| **Check** | CI job: regenerate to a temp file, `diff` against the committed artifact, non-zero exit fails the build. |
| **Priority** | **Blocking.** Without it `XR-COL-01` is a convention, not a guarantee. |

### XR-COL-03 — The registry is the picker's inventory, not a parallel list

| | |
|---|---|
| **Statement** | The picker renders exactly the stops the registry contains, in registry order, with no locally-declared subset, reorder or addition. |
| **Surfaces** | Phone (settings, join) |
| **Rationale** | Today's picker couples `PRESET_NAMES` to `SINGER_COLORS` **by array position**, and its own comment records that no guard can detect a consistent same-length reorder — at 8 entries a human can still read it; at 48 nobody will. |
| **Source** | `apps/core/src/lib/components/ColourPicker.svelte:35–50` and `apps/core/src/lib/design-system.test.ts:175–187` (the length-parity guard, and its stated inability to check order). |
| **Acceptance** | **Given** the rendered picker, **When** its swatches are read in DOM order, **Then** the sequence of their colour values equals `variants.chromatic.stops[].fill` in registry order, and the count is 48. |
| **Check** | Rendered-DOM assertion where reachable; otherwise a source scan asserting the picker's swatch list is a direct `map` over the registry import with no intervening literal array. Note the rendered rung is currently blocked for components importing `$app` (see `apps/core/src/lib/tv/wake-lock.test.ts:18–27`). |
| **Priority** | **High.** This is what retires the by-position name coupling instead of scaling it 6×. |

### XR-COL-04 — Every stop is measured against the surfaces the app actually paints

| | |
|---|---|
| **Statement** | The registry's contrast figures are computed against the live values of **every surface the app actually paints a stop's value on**, read from `apps/core/src/app.css` — at minimum `--bg`, `--card`, `--card2`, `--card-tint` and `--card-tint2` — and no stop ships failing the role thresholds in `XR-COL-05`–`XR-COL-07` against those values. The surface list is **derived from the read sites, not hand-maintained**, so a new read site on a new surface fails the build rather than passing unmeasured. |
| **Surfaces** | Phone, TV, operator dashboards, build |
| **Rationale** | The generator's `surfaces` block (`#060a18` / `#131a2e` / `#1a2238`) is not the app's (`#0b0b12` / `#1a1a28` / `#212133`), and against the real `--card` six stops fall below AA as ink. |
| **Source** | `packages/shared/src/player-palette-48.json` `surfaces`; `apps/core/src/app.css:7–10`. Failure list `DERIVED` — model as stated in the finding above. |
| **Acceptance** | **Given** the registry and `app.css`, **When** the surface hexes are extracted from `app.css` and compared to the registry's `surfaces`, **Then** they are equal; **and when** `--card` is changed in `app.css` without regenerating, **Then** the comparison fails rather than the suite staying green. |
| **Check** | The same token-reading helper `contrast.test.ts` already uses (`token('card')`), applied to the registry's `surfaces` block and to all 48 stops' four roles. |
| **Priority** | **Blocking.** Six known AA failures, and the mechanism that hid them is the one the handoff flags as the landmine to fix first. |

## Group 2 — The four per-stop contrast roles

Thresholds are per role, not per palette. All four are per-stop obligations: "the palette passes"
is not a checkable statement, "stop 39 passes role 4" is.

### XR-COL-05 — A stop's fill is visible as an identity dot on both dark surfaces

| | |
|---|---|
| **Statement** | Every stop's `fill` reaches at least **3:1** against `--bg` and against `--card`. |
| **Surfaces** | Phone, TV (the singer dot and roster chip are the TV's only player-coloured elements) |
| **Rationale** | The dot is a non-text UI object whose whole job is telling two guests apart across a room. |
| **Source** | [WCAG 2.2 SC 1.4.11 Non-text Contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html); threshold already encoded as `MIN_DOT_CONTRAST = 3` at `packages/shared/src/colors.ts:51`. |
| **Acceptance** | **Given** the 48 stops, **When** each `fill` is measured against both surfaces, **Then** the minimum is ≥ 3.0. Worst cases against the app's tokens: **Orchid 3.73 on `--bg`, 3.27 on `--card`** (`DERIVED`, model above). Falsified by any stop measuring < 3.0 on either. |
| **Check** | Unit test in `colors.test.ts`, reading surfaces via the token helper and stops from the registry. |
| **Priority** | **Blocking.** |

### XR-COL-06 — A stop's `onFill` is the only ink permitted on its fill, and clears AA

| | |
|---|---|
| **Statement** | Every stop declares one `onFill`, it measures at least **4.5:1** against that stop's `fill`, and no surface painted in a stop's `fill` carries any other text colour. |
| **Surfaces** | Phone (primary CTA, add button, active chip), operator dashboards. **Not TV** — the stage keeps neutral chrome and never fills a text-bearing surface with a player's colour. |
| **Rationale** | `onFill` is **36 dark / 12 white** — per-stop, not one rule — so "white on the accent" is now wrong for 36 of 48 and there is no global answer to fall back on. |
| **Source** | [WCAG 2.2 SC 1.4.3 Contrast (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html); split and worst case from handoff §2 (`min_label` 4.53). |
| **Acceptance** | **Given** the 48 stops, **When** each `onFill` is measured against its own `fill`, **Then** the minimum is ≥ 4.5 — worst case **Scarlet 4.53** (surface-independent, so the handoff figure stands unchanged). **And given** the source tree, **When** rule blocks setting `background: var(--singer)` (or the fill token) are collected, **Then** each either sets `color: var(--singer-on)` or sets no `color` at all. |
| **Check** | Unit test for the ratios; source scan for the pairing, in the shape of `contrast.test.ts:241` (`no rule puts a text color on var(--grad)`). |
| **Priority** | **Blocking.** |

### XR-COL-07 — A stop's `ink` clears AA as text on a card

| | |
|---|---|
| **Statement** | Every stop declares an `ink` value that measures at least **4.5:1** against `--card`, and accent-coloured *text* is drawn only in `ink`, never in `fill`. |
| **Surfaces** | Phone, operator dashboards |
| **Rationale** | `ink` differs from `fill` for **13 of 48** (Redline, Scarlet, Cerulean, Cobalt, Denim, Periwinkle, Iris, Violet, Magenta, Fuchsia, Orchid, Rose, Hibiscus) — the deep stops cannot be their own card ink. |
| **Source** | [WCAG 2.2 SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html); the 13-stop list from handoff §2. |
| **Acceptance** | **Given** the 48 stops, **When** each `ink` is measured against `--card` as read from `app.css`, **Then** every stop is ≥ 4.5. **Was falsified for six stops** — Cobalt 4.47, Denim 4.48, Magenta 4.48, Orchid 4.48, Rose 4.48, Fuchsia 4.49 (`DERIVED`, model above) — **fixed in #820** by regenerating against the real surfaces with a declared 0.05 margin; worst is now 4.56. |
| **Check** | Unit test per stop; the six named stops are the regression fixture. |
| **Priority** | **Blocking.** |

### XR-COL-08 — Contrast tests read tokens; they never restate them

| | |
|---|---|
| **Statement** | No test asserting a contrast figure contains a hex literal that duplicates a token declared in `app.css`. |
| **Surfaces** | Build |
| **Rationale** | `packages/shared/src/colors.test.ts:32–33` hard-codes `#0b0b12` and `#1a1a28`, tied to `--bg`/`--card` by a trailing comment only, so changing either token leaves three contrast tests passing while measuring colours the app no longer paints — and `XR-COL-04` shows that exact mechanism already producing six unnoticed AA failures. |
| **Source** | `packages/shared/src/colors.test.ts:32–33`; the token declarations at `apps/core/src/app.css:7–10`. |
| **Acceptance** | **Given** every `*.test.ts` under `packages/shared/src` and `apps/core/src`, **When** hex literals in them are compared against the set of hexes declared in `app.css`'s `:root`, **Then** the intersection is empty. |
| **Check** | Source scan, using the token-reading helper `contrast.test.ts` already has. |
| **Priority** | **Blocking, and first.** Everything in Groups 2 and 3 measures nothing until this holds. |

### XR-COL-09 — No two stops collapse onto one rendered colour

| | |
|---|---|
| **Statement** | The 48 `fill` values are 48 distinct canonical 6-digit lowercase hexes, and each stop is perceptually separated from its neighbours. |
| **Surfaces** | Phone, TV |
| **Rationale** | Two guests who render identically on the TV roster have no identity marker at all, and gamut clipping is the mechanism that silently merges two stops — clipping hue-shifts rather than desaturating. |
| **Source** | `packages/shared/src/colors.ts:140–155` (`hueToHex`'s no-clip guarantee and why it exists); separation figures from handoff §2 — min neighbour ΔE 0.0319, min pair ΔE 0.0225 (Viridian/Emerald), `dup_hex: 0`. |
| **Acceptance** | **Given** the registry, **When** the 48 `fill` values are put in a set, **Then** its size is 48 and every value matches `/^#[0-9a-f]{6}$/`; **and when** pairwise OKLab ΔE is computed, **Then** the minimum is ≥ 0.0225 and the minimum neighbour ΔE is ≥ 0.0319. |
| **Check** | Unit test; the ΔE floors are pinned to the generator's own reported minima so a regeneration that degrades separation reds instead of shipping. |
| **Priority** | **High.** |

**Recommendation (not decided):** whether the ΔE floors are the *bar* or merely *today's measured
value* is a judgement nobody has made. Pinning them at the current minima means any future
regeneration that shifts a stop by a hair fails. That is the intended behaviour for a generated
artifact, but it will read as a broken test the first time it fires.

## Group 3 — Token-layer consequences

### XR-COL-10 — `--accent-ink` remains a required, distinct token

| | |
|---|---|
| **Statement** | The token layer declares an accent-as-ink token separate from the accent fill, and every accent-coloured text node reads the ink token. |
| **Surfaces** | Phone, operator dashboards |
| **Rationale** | `ink ≠ fill` for 13 of 48 stops, so collapsing the two silently downgrades those 13 to sub-AA text. |
| **Source** | Handoff §2 ("`--accent-ink` remains a required, distinct token; do not collapse it into `--accent`"); the token's existing rationale at `apps/core/src/app.css:60–62`. |
| **Acceptance** | **Given** the token layer, **When** the accent-ink token is resolved for each of the 13 divergent stops, **Then** it equals that stop's `ink` and not its `fill`. Falsified by any build where the two tokens resolve to the same value for a divergent stop. |
| **Check** | Unit test over the 13 named stops. |
| **Priority** | **Blocking.** |

### XR-COL-11 — `--accent-strong` is retired, not carried forward

| | |
|---|---|
| **Statement** | No token exists whose definition is a darkened derivative of the player's fill; the fill itself is the actionable accent that carries `onFill`. |
| **Surfaces** | Phone, operator dashboards |
| **Rationale** | `--accent-strong` exists for exactly one reason — a 3% darken so white reaches 4.88:1 — and per-stop `onFill` supersedes that reason entirely; keeping it would be a second accent with no rule for when to use it. |
| **Source** | `apps/core/src/app.css:31–36` (the token and its stated sole purpose); handoff §3 ("`--accent-strong` loses its job"). |
| **Acceptance** | **Given** the token layer and the source tree, **When** `--accent-strong` is searched for, **Then** zero declarations and zero `var()` reads remain. Note this also removes the *left half* of `contrast.test.ts:158`'s pair test and one of the two tokens scanned at `contrast.test.ts:177`, so those must be handled under `XR-COL-18` rather than left to fail. |
| **Check** | Source scan; plus the guard-retirement record required by `XR-COL-18`. |
| **Priority** | **High.** |

### XR-COL-12 — Fill and its ink are emitted as one pair, per stop, and never separately

| | |
|---|---|
| **Statement** | Whenever a surface is painted in a stop's `fill`, that stop's `onFill` is set in the same place, from the same registry lookup; neither is ever set from a literal or from a different stop. |
| **Surfaces** | Phone, operator dashboards |
| **Rationale** | `--on-accent` stops being the constant `#ffffff` and becomes one of 48 values, so the pairing that used to be guaranteed by there being one ink now has 48 chances to go wrong. |
| **Source** | `apps/core/src/app.css:37–38` (the current pair and the stated reason they are declared adjacently — "so the two can never drift apart"); handoff §3. |
| **Acceptance** | **Given** the source tree, **When** every rule block or style binding that sets a fill custom property is collected, **Then** each also sets the matching ink property, and for every stop the resolved pair measures ≥ 4.5:1 (per `XR-COL-06`). Falsified by one site setting the fill alone. |
| **Check** | Source scan for the pairing; unit test for the 48 ratios. |
| **Priority** | **Blocking.** 48 pairs is the reason, not the mitigation. |

### XR-COL-13 — The gradient stays decoration-only, and that is now a per-stop question

| | |
|---|---|
| **Statement** | No text label is drawn on the brand gradient, on any stop. |
| **Surfaces** | Phone, TV, operator dashboards |
| **Rationale** | The ban was justified by one fixed measurement (white on the pink stop, 2.84:1); with `accent2` derived per stop at +42° hue, the gradient is now 48 different gradients and no single measurement licenses a label on any of them. |
| **Source** | [WCAG 2.2 SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html); the ban and its measurement at `apps/core/src/app.css:22–30`; the existing guard at `apps/core/src/lib/contrast.test.ts:241`. |
| **Acceptance** | **Given** the source tree, **When** rule blocks containing the gradient token are collected, **Then** none sets a `color` other than the `background-clip: text` wordmark exemption already carved out at `contrast.test.ts:248`. The guard's *justifying* measurement must additionally be re-stated per stop, or explicitly recorded as unmeasured. |
| **Check** | The existing `contrast.test.ts:241` scan survives unchanged; what changes is the comment above it, which currently asserts one number as the reason. |
| **Priority** | **High.** The rule holds; the *reason* recorded next to it becomes false, and a false reason invites someone to re-derive it and reach the wrong answer. |

### XR-COL-14 — Player hues are never registered as Tailwind theme colours

| | |
|---|---|
| **Statement** | The player fill, ink, `onFill` and `accent2` values are declared in `:root` only, and never registered in Tailwind's `@theme`. |
| **Surfaces** | Phone, operator dashboards, build |
| **Rationale** | Registering a colour in `@theme` mints the whole utility family with no per-family opt-out, so `--color-accent` produces `text-accent` beside `bg-accent` — handing every developer a one-class route around `XR-COL-07`'s ink/fill distinction and around the pairing rule in `XR-COL-12`. |
| **Source** | Shared brief, *Library — DECIDED* ("Tailwind has one sharp restriction… never register them; use `@theme` for non-colour tokens only"). |
| **Acceptance** | **Given** the Tailwind config and CSS entry, **When** the `@theme` block's declarations are enumerated, **Then** none is a `--color-*` mapping to a player token. Falsified by one such registration. |
| **Check** | Source scan of the `@theme` block. Applies only once Tailwind lands; until then, `EXEMPT` with the trigger named. |
| **Priority** | **High**, from the moment Tailwind is introduced. |

## Group 4 — The picker is a discrete grid

### XR-COL-15 — The colour control offers exactly the 48 registry stops and nothing between them

| | |
|---|---|
| **Statement** | The player-colour control is a grid of 48 discrete swatches. No continuous hue input exists, and no value outside the registry can be produced by any control. |
| **Surfaces** | Phone (join, settings) |
| **Rationale** | Chromatic varies lightness and chroma per stop, so a colour *between* two stops has no validated `onFill` and no measured contrast for any of the four roles — it is not a colour the product can honour. |
| **Source** | Handoff §2, *The picker is now a discrete grid, not a free wheel — IMPORTANT*. |
| **Acceptance** | **Given** the rendered control, **When** its inputs are enumerated, **Then** there is no `input[type=range]` or other continuous hue affordance, and the set of emittable values equals the 48 registry fills exactly. |
| **Check** | Source scan for a continuous hue input in the picker; plus `XR-COL-03`'s inventory assertion. Whether 48 swatches at ≥ 44px are usable in one thumb-reachable grid is a rendered-layout judgement — `EXEMPT`, deferred to build. |
| **Priority** | **Blocking.** A free wheel emits colours the palette cannot certify. |

### XR-COL-16 — Nearest-stop matching is full OKLab ΔE, or it does not exist

| | |
|---|---|
| **Statement** | Any surviving "nearest stop to an arbitrary colour" behaviour selects by full OKLab ΔE across all 48 stops, including the lightness axis. |
| **Surfaces** | Phone (settings), and any legacy-row rendering path |
| **Rationale** | `nearestSingerHue` compares only the OKLab chromatic axes and deliberately ignores lightness — correct when every candidate sat at one pinned L, wrong now that L ranges 0.56–0.88, because it will return a stop whose lightness is far from the input's. |
| **Source** | `packages/shared/src/colors.ts:377–394` (the function, and the comment stating lightness is deliberately ignored); the same file at `:265–269` records this exact mode of failure already measured — the chromatic-axes comparison mis-snapped **15 of 24** stage-tier hues. Handoff §2 ratifies the re-derivation. |
| **Acceptance** | **Given** the 48 stops, **When** each stop's own `fill` is fed to the matcher, **Then** it returns that stop (round-trip identity); **and when** a colour is fed whose hue matches stop A but whose lightness matches distant stop B, **Then** the result is the stop with the smaller full ΔE, not the nearer hue angle. Falsified by a hue-only implementation, which fails the second case. |
| **Check** | Unit test with the round-trip plus at least one lightness-discriminating fixture. If no nearest-stop behaviour survives, the function is deleted, which satisfies this row trivially and must be recorded under `XR-COL-18`. |
| **Priority** | **High.** |

## Group 5 — The colour name carries identity without colour

### XR-COL-17 — Every stop has a unique name, shown wherever the colour identifies someone

| | |
|---|---|
| **Statement** | Each of the 48 stops has one unique human-readable name, sourced from the registry, and that name is rendered as text — not only as an accessible label — in the picker and in the roster. |
| **Surfaces** | Phone (picker, roster), TV (roster chip) |
| **Rationale** | For a colour-blind guest the dot is not an identifier, so the name is the actual carrier of identity; and names are assigned from each stop's **measured sRGB hue**, not its OKLCH angle, because the two disagree sharply (OKLCH 199° is cyan, not mint) and a first pass mislabelled a dozen swatches. |
| **Source** | [WCAG 2.2 SC 1.4.1 Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html); handoff §2 (*Facts about this table you must not lose* — "the name is also the non-colour carrier of identity for a colour-blind guest — keep it visible in the picker and the roster"). |
| **Acceptance** | **Given** the registry, **When** the 48 names are put in a set, **Then** its size is 48. **And given** the rendered picker, **Then** the selected stop's name appears as visible text. **And given** the rendered roster, **When** a member row is read, **Then** the stop name appears as text alongside the display name. Falsified today: `apps/core/src/lib/tv/TvLobby.svelte:136` renders a swatch plus the display name and no colour name. |
| **Check** | Unit test for name uniqueness and registry sourcing; rendered assertion for the two surfaces where reachable. Whether the TV roster chip can carry the name without crowding at 8–12 ft is a layout judgement — `EXEMPT`, deferred to build with the frame as evidence. |
| **Priority** | **High.** |

**Note on the accepted status-hue cost.** The owner has **accepted** that 20 of 48 stops sit within
20° of a status hue (6 near failure red, 5 near waiting amber, 9 near ready green). Arcs are not
reserved and no stop is removed. Recording the cost accurately matters because **rendering it
inverted the intuition**: the **error survives** a same-hue accent — its tint, border and pill
carry it — so the case that looked worst is the mildest. What degrades is the **status pill's
scannability**: with an amber or green accent, every row's add button wears the colour you are
sweeping the list for. **Green is the worst**, because "Ready" is the most common badge in the app.
The harm is **not a false alarm** — both meanings are positive — it is that **the chip stops being
scannable, which is the only job the chip has.** The three status colours themselves are fixed and
never follow the player; that is covered by existing tokens (`--ok`, `--warn`, `--danger` and their

## Requirements deliberately NOT written, and why

1. **The three status colours must not follow the player.** Already both stated and enforced —
   `--danger` carries its own rationale at `app.css:67–69` ("NOT `--accent2`: pink is also a valid
   singer colour"), and each status colour has a paired tinted surface and line. Rewriting it as new
   would bury the rows above that *are* at risk.
2. **Reserved hue arcs, or removal of the 20 near-status stops.** The owner accepted the proximity.
   Specifying against it would be re-litigating a ratified decision; the accepted cost is recorded
   under `XR-COL-17` instead.
3. **"Render the row-level `+` in neutral ink."** Explicitly **not adopted** in the handoff and
   offered for judgement during build. It is recorded as a documented option, not a requirement, and
   deliberately has no guard — a guard would adopt it by the back door.
4. **The `--grad` decoration-only ban as a new rule.** It already exists, is already guarded
   (`contrast.test.ts:241`), and survives the palette change intact. `XR-COL-13` addresses only the
   part that genuinely breaks: the single measurement recorded as its reason.
5. **A stated aesthetic brief for the palette.** Handoff §4 records that no document in the repo
   says what Encore should *feel* like, and every recorded colour decision is a contrast decision.
   Writing a "the palette expresses X" requirement would invent the answer. This stays open, and it
   is the reason every row here is a measurement rather than a taste.
6. **A swatch size / grid-geometry number for the 48-stop picker.** `--tap: 44px` is a hit-area
   floor, not a paint size, and nothing in the repo establishes how 48 targets fit one thumb-reachable
   phone grid. Any number here would be invented; routed to `EXEMPT` inside `XR-COL-15` with the
   frame as evidence.
7. **A per-stop measurement licensing a label on any stop's gradient.** The handoff explicitly
   declines to assume one exists. `XR-COL-13` keeps the ban and requires the missing measurement be
   recorded as missing, rather than supplying a number nobody took.
8. **Any requirement about the `uniform` variant.** It is in the JSON (`variants.uniform`, 48 stops,
   `min_dot_bg` 7.19 / `min_label` 7.02) and was rejected because pinning L=0.72 removes true yellow
   and true blue. It is a rejected alternative, not a shipping surface.
9. **Colour-blind simulation thresholds.** No published standard sets a minimum confusion-line
   separation for an identity palette, and WCAG 1.4.1 asks for a non-colour carrier rather than a
   separable palette — which is why `XR-COL-17` requires the **name** instead of a deuteranopia
   metric. Recorded as `UNSOURCED`: I looked for a citable threshold and found none.
