# The KNOWN-GOOD transitive version set for the worker, as a pip/uv CONSTRAINTS file.
#
# WHY THIS EXISTS. requirements.txt pins 16 DIRECT dependencies, which resolved to 128 installed
# packages — so 112 transitive versions were decided by whenever you happened to install. Measured on
# the day this file was created, a fresh resolve of the same requirements.txt already disagreed with a
# working venv on 15 packages, including filelock 3.32.6 -> 4.0.3 across a major version. That is where
# "works on my machine" comes from on an ML stack.
#
# WHY A CONSTRAINTS FILE AND NOT A LOCKFILE. A single cross-platform lock is impossible here, and not
# by choice: `audio-separator==0.47.0` requires `torch>=2.13` on darwin-arm64 while this stack pins
# `torch==2.8.0`, which is exactly why requirements.txt marker-excludes it on Apple Silicon. A universal
# resolve therefore has no solution, and a per-platform lock generated on a Mac would silently drop
# audio-separator for everyone on Linux. Constraints apply per platform: uv (or pip) still resolves the
# right marker-gated set for the box it is on, and every version it picks is pinned to the one below.
#
# HOW TO REGENERATE, deliberately rather than incidentally:
#   cd worker && .venv/bin/pip freeze --exclude-editable | grep -vE "^(pip|setuptools|wheel)==" > constraints.txt
# Do that from a venv you have actually RUN the suite against, and review the diff — every line here is
# a version somebody verified, not a version somebody resolved.
#
# `karaoke-lyrics-processor` is deliberately absent: it is installed --no-deps (see dev.sh and
# worker/Dockerfile), so its version is pinned at those call sites and its 30-package dependency list
# must never be resolved.
#
# Consumed by dev.sh. worker/Dockerfile still installs via plain pip against requirements.txt; adding
# `-c constraints.txt` there would make dev and prod resolve identically, and
# tests/guards/subsystem-jobs/worker-constraints.test.ts is what stops the two inputs drifting apart.
